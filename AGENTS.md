# DMK development and receiving maintenance

Use the existing checkout, environments, commands and receiving bindings. Preserve
other work and each being's separate memory authority. Never put private memory,
source conversations, credentials or receiving access paths in GitHub artifacts.

Read `docs/resource-lifecycle.md` before creating full database copies, packaging
a runtime or retaining a qualification corpus. Put large outputs on the receiving
data volume. Runtime packages contain executable resources, not the research
corpus. Reuse valid evidence and fixtures instead of repeating model calls.

Use the receiving backup policy. Qualified periodic profiles do not copy the
whole database before ordinary memory/index writes. Use `backupctl begin --critical`
for consequential maintenance; see docs/periodic-backups.md.
Protect unfinished operations and concrete rollback dependencies. A backup's
completion/retention must be explicit; do not leave untracked full copies after
every edit. Keep compact preserved originals within an explicit byte budget.

At experiment closure, keep source/version references, results, costs and enough
inputs to reproduce the finding. Retire proven disposable copies or compact cold
evidence with verified restoration, leaving a discoverable manifest. Preserve
active writers and unresolved work. Do not requeue old experiments as maintenance.

Follow the human's current deployment/Stop authorization. Resource cleanup does
not authorize a global Stop, new services, private-history intake or paid replay.
